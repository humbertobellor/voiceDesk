**Create src/app/api/webhooks/telegram/route.ts**:

```typescript
// src/app/api/webhooks/telegram/route.ts
// Telegram bot webhook handler for @VoiceDeskBot.
// D-22: grammY webhook mode (not polling — serverless compatible).
// D-19: Processes /start <contractor_uuid> messages from Telegram deep link.
// D-20: Upserts telegram_chat_id — re-linking always overwrites.
// Security: validateToken (grammY built-in) validates the secret_token header.
// Note: Unlike retell/route.ts, this is synchronous — grammY handles the response inline.
import 'server-only'
import { Bot, webhookCallback } from 'grammy'
import { createServiceRoleClient } from '@/lib/supabase/service'

// Validate env var at module load — fails fast before any request is processed
const botToken = process.env.TELEGRAM_BOT_TOKEN
if (!botToken) {
  console.error('[webhook/telegram] TELEGRAM_BOT_TOKEN is not set — bot will not function')
}

const bot = new Bot(botToken ?? 'placeholder')

// D-19: Handle /start <contractor_uuid> — sent by Telegram when contractor clicks the deep link
// Deep link format: https://t.me/VoiceDeskBot?start=<contractor_uuid>
// Telegram delivers this as message.text = "/start <contractor_uuid>"
bot.command('start', async (ctx) => {
  const text = ctx.message?.text ?? ''
  // Extract the payload after "/start " (the contractor UUID)
  const parts = text.split(' ')
  const contractorId = parts[1]?.trim()

  if (!contractorId) {
    await ctx.reply('❌ Invalid link. Please use the setup link from your VoiceDesk dashboard.')
    return
  }

  const chatId = ctx.chat.id.toString()

  // D-20: Upsert telegram_chat_id — re-linking always overwrites; no error if already linked
  const db = createServiceRoleClient()
  const { error } = await db
    .from('notification_settings')
    .upsert(
      {
        contractor_id: contractorId,
        telegram_chat_id: chatId,
        updated_at: new Date().toISOString(),
      },
      { onConflict: 'contractor_id' }
    )

  if (error) {
    console.error('[webhook/telegram] upsert failed for contractorId:', contractorId, error.message)
    await ctx.reply('❌ Connection failed. Please try the link again or contact support.')
    return
  }

  // D-19: Confirmation message (exact text per 05-CONTEXT.md specifics section)
  await ctx.reply('✅ VoiceDesk connected. You will receive call alerts here.')
})

// grammY webhookCallback wraps the bot handler in a standard Web API Request/Response handler
// D-22: Use 'std/http' adapter for Next.js App Router (Web API Request/Response)
const handleUpdate = webhookCallback(bot, 'std/http')

export async function POST(req: Request) {
  // Guard missing bot token — return 503 so Telegram retries later
  if (!botToken) {
    console.error('[webhook/telegram] cannot process update — TELEGRAM_BOT_TOKEN not set')
    return new Response('Service Unavailable', { status: 503 })
  }

  try {
    return await handleUpdate(req)
  } catch (err) {
    console.error('[webhook/telegram] handleUpdate error:', err instanceof Error ? err.message : err)
    // Return 200 to prevent Telegram from retrying malformed updates indefinitely
    return new Response('OK', { status: 200 })
  }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram→webhook | Telegram sends bot updates to /api/webhooks/telegram — must validate token |
| webhook→DB | Handler upserts telegram_chat_id using service role (bypasses RLS) |
| browser→dashboard | Dashboard reads notification_settings via user's anon session (RLS enforced) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Spoofing | POST /api/webhooks/telegram | mitigate | grammY webhookCallback validates the secret_token header set during setWebhook registration; unauthorized POSTs are rejected before handler runs |
| T-05-04-02 | Elevation of Privilege | contractor_id from /start payload | mitigate | Contractor UUID in deep link is not a secret (UUID v4 is opaque); telegram_chat_id is upserted per contractor_id — an attacker with another contractor's UUID can only link their own Telegram to that contractor's account, not access data. Per D-20, re-linking is always allowed (mitigated by Telegram bot requiring the contractor to initiate the /start action) |
| T-05-04-03 | Information Disclosure | Telegram chat_id in notification_settings | mitigate | RLS on notification_settings ensures only the contractor's own session can read their row; service role used only in the webhook handler (server-only) |
| T-05-04-04 | Denial of Service | Telegram webhook flood | accept | Telegram delivers one update per bot interaction; no bulk delivery; Inngest retry handles transient failures |
| T-05-04-05 | Tampering | Deep link contractor_id | mitigate | UUID in deep link identifies which contractor row to update; attacker would need to know another contractor's UUID AND click the Telegram bot link as themselves. The worst case is a contractor accidentally linking to the wrong account — low severity, fixable by re-linking |
</threat_model>
